## 재현된 문제

### 1. [P1] 이전 자동 주행의 저장 완료가 다음 주행의 복구 파일을 삭제한다

- 위치: `lib/main.dart:83`, `lib/services/route_auto_record_service.dart:269`, `lib/services/run_session_service.dart:30`.
- 자동 주행 종료는 상태를 idle로 바꾸고 저장 콜백을 기다리지 않는다. 그 사이 새 주행을 시작할 수 있다. 이전 저장이 끝나면 `sessions.clearRecovery()`가 현재 파일을 주행 ID 확인 없이 지운다.
- 재현: 자동 주행 A의 저장 완료를 지연 → B 시작 → 31초 경과 후 B의 실제 스냅샷 쓰기 → A 저장 완료. **B는 recording인데 복구 스냅샷이 null**이 됐다.
- 영향: 다음 스냅샷이 쓰이기 전에 앱이 종료되면 B의 복구 기록을 잃는다. 이미 저장된 A의 DB 기록이 삭제된다는 뜻은 아니다.
- 수정: 완료한 `runId`를 전달해 해당 기록만 정리하고, 확인·삭제를 스냅샷 쓰기와 같은 직렬 큐 안에서 처리한다. 저장 전 주행별 복구 파일을 보관하는 방식도 가능하다. 새 주행 시작 시 이전 미저장 복구 파일을 무조건 지우는 처리도 함께 점검한다.

### 2. [P2] 폰에 저장된 리포트도 인터넷 응답을 기다린다

- 위치: `lib/services/run_history_service.dart:417`, `lib/screens/lean_app_shell_screen.dart:1114`.
- 클라우드 저장이 켜져 있고 소유권이 일치하면 `loadDetail()`은 서버 조회부터 기다린다. 로컬 상세는 서버가 null을 반환한 뒤 읽는다. 기록 행을 누른 화면도 상세가 돌아올 때까지 화면 전환을 기다린다.
- 재현: 로컬 상세가 존재함을 확인한 뒤 서버 응답을 보류. 로컬 파일이 있어도 열기 Future가 끝나지 않았다. 서버를 null로 완료한 후에야 상세를 반환했다.
- 수정: **로컬 → 업로드 대기 데이터 → 원격** 순으로 읽는다. 원격에만 있는 기록은 즉시 로딩 화면을 열고 재시도·취소 경로를 제공한다. 빠른 반복 탭에 대한 중복 화면 열기도 막는다.

### 3. [P2] 늦게 도착한 초기 GPS가 사용자의 지역 검색과 충돌한다

- 위치: `lib/screens/lean_route_finder_screen.dart:382`, `:414`, `:511`.
- 지역 선택에는 세대 번호 검사가 있지만 최초 `_searchCurrentLocation()`에는 없다. 명시적으로 다른 지역을 고른 뒤에도 초기 위치 조회가 완료되면 해당 위치의 루트를 새로 요청한다.
- 화면 재현: GPS를 보류한 상태에서 장소 검색으로 Montreal 선택 → 지도 중심 45.5017 확인 → 늦은 GPS를 Seoul로 완료. **지도 중심은 Montreal인데 두 번째 루트 필드 요청은 Seoul(37.5665)**이었다.
- 이 테스트는 가짜 루트 서비스로 요청 위치와 지도 중심의 불일치를 확인했다. 실제 서울 서버 데이터까지 불러와 비교한 것은 아니다. 실제 RouteService는 나중 요청에 새 토큰을 주므로 앞선 지역 요청을 무효화할 수 있다.
- 수정: 초기 GPS, 지역 선택, 지도 영역 검색을 하나의 검색 세대 번호로 관리한다. 사용자가 지역을 선택했다면 이전 자동 GPS 결과는 화면/루트 필드에 적용하지 않는다.

### 4. [P2] GPS 대기 시간이 단계마다 다시 시작된다

- 위치: `lib/services/location_service.dart:239–281`.
- 기존 추적 스트림 대기 → 임시 스트림 대기 → 단발 GPS 요청이 각각 전체 timeout을 사용한다. 마지막 위치 조회에도 이 함수의 전체 제한 시간이 적용되지 않는다.
- 재현: 각 timeout을 80ms로 설정하고 모든 위치 공급을 보류하면 **약 250ms** 후 끝난다. 5초 설정은 세 단계가 모두 소진될 때 약 15초, 6초 설정은 약 18초의 대기 경로가 된다. 플랫폼이 즉시 오류를 반환하면 더 짧을 수 있다.
- 수정: 전체 작업의 deadline 하나를 두고 남은 시간만 사용한다. 유지 중인 스트림을 우선 재사용하고, UI는 위치 결과와 독립적으로 지역 검색을 허용한다. 위치 재시도가 네트워크 루트 요청까지 중복시키지 않도록 한다.

### 5. [P2] 동기화할 때 변경 없는 주행 상세도 전부 다시 업로드한다

- 위치: `lib/services/run_history_service.dart:187–198`.
- 원격 summary ID가 이미 있어도 모든 로컬 상세를 읽어 pending에 저장하고 `uploadRunDetail()`을 다시 호출한다. 성공 여부/변경 여부를 상세별로 기록하지 않는다.
- 재현: 같은 기록을 수정하지 않고 두 번 동기화 → 상세 업로드 횟수 **1 → 2**. 가짜 클라우드는 첫 성공 이후에도 원격 ID를 유지했다.
- 영향: 기록이 쌓일수록 앱 실행 시 동기화의 네트워크·직렬 큐·로컬 읽기/쓰기 비용이 늘어난다. 그 큐를 기다리는 삭제/다른 동기화 작업에도 영향을 줄 수 있다.
- 수정: 기록 상세별 dirty/version/hash 또는 업로드 완료 상태를 영속화한다. 신규·실패·수정 기록만 전송하고, 원격 누락 복구를 위한 별도 대조 경로를 남긴다. 요약 ID 존재만으로 상세 업로드 성공을 추정하면 안 된다.

### 6. [P2] 작은 화면에서 리포트가 넘치고 큰 글씨에서는 주행/탐색도 넘친다

- 위치: `lib/screens/lean_run_summary_screen.dart:1219`, `:2181`; `lib/screens/lean_drive_screen.dart:807`; `lib/screens/lean_route_finder_screen.dart:2884`.
- 기존 430×1200 화면 테스트를 **375×667 논리 픽셀**로 복제했다. 기본 글씨에서도 리포트 카드 Column이 **6.5px** 넘쳤다.
- 글씨 1.5배: 리포트 카드 **16–83px**, 주행 Column **13px**, 위치 안내 Row **21px** 넘침. 리포트는 2열·고정 비율 1.55와 큰 숫자/패딩이 겹친다. 탐색 안내는 긴 액션 버튼이 좁은 Row 안에서 공간을 차지한다.
- 수정: 리포트 카드 높이를 내용/글씨 크기에 맞추고 필요 시 1열로 전환한다. 주행 핵심 조작 버튼의 자리를 확보하면서 보조 패널을 접거나 스크롤 가능하게 한다. 빈 상태 안내 액션은 좁은 폭에서 아래 줄로 내린다. 글씨 크기를 강제로 제한해서 해결하지 않는다.
- 검증 제한: Flutter 레이아웃 테스트이며 기본 테스트 폰트 조건이다. 네이티브 지도는 테스트 대체 화면이다. 실제 기기의 safe area, 한국어·프랑스어 및 접근성 크기에서도 확인해야 한다.

### 7. [P2] DB 최초 열기 실패가 캐시되어 같은 서비스의 재시도가 실제로 재시도하지 않는다

- 위치: `lib/services/run_local_store.dart:45`, `lib/main.dart:42`.
- `_opening ??= _open()`이 실패한 Future도 보관한다. 다음 호출은 같은 실패를 다시 받는다. 앱 시작에서는 `history.load()`가 끝나야 `runApp()`까지 도달한다.
- 재현: DB 경로 준비 단계에 일시 오류 주입 후 `loadRuns()` 두 번 실행. 경로 준비 함수 호출은 **1회**, 두 조회 모두 실패했다.
- 수정: 열기 실패 시 해당 `_opening`을 해제해 재시도할 수 있게 하고, 초기 로컬 저장소 오류를 보여주는 부팅 UI를 제공한다. 진행 중인 정상 open의 공유는 유지한다. 실제 DB 손상/디스크 용량 부족 원인까지 이 테스트로 검증한 것은 아니다.

## 더 가볍게 만들기: 우선순위

1. **중복 업로드 제거 + 로컬 리포트 우선 읽기.** 반복 비용을 실제로 재현했고 제품 기능을 덜어낼 필요가 없다.
2. **첫 프레임 전에 기다리는 일을 줄이기.** `main.dart:30–42`는 인증 초기화 → 설정 → 탐험 데이터 → 기록 로드를 기다린 뒤 앱을 그린다. `SupabaseService.init()`에는 익명 로그인/세션 복구 네트워크가 포함된다. 먼저 부팅/로컬 화면을 그리고 인증 완료 후 루트 요청을 연결하는 방식이 적절하다. 인증 전 API를 무작정 호출하자는 뜻은 아니다. 이번에는 새 콜드 스타트 시간을 측정하지 않았다.
3. **위치 값과 지도 데이터의 rebuild 범위 분리.** Finder `build()`는 LocationService 전체를 watch하면서 루트 랭킹·클러스터·지도 후보를 다시 만든다(`lean_route_finder_screen.dart:1269–1318`). Drive는 IMU 변화 때 상위 화면에 setState를 호출한다(`lean_drive_screen.dart:633`). 지도/루트 모델은 데이터·필터·카메라 영역이 달라질 때 계산하고 속도/G 표시를 작은 위젯으로 분리할 수 있다. 실제 배터리/프레임 개선량은 Profile 모드 실기기로 검증해야 한다.
4. **리포트 불변 계산 캐시.** 리플레이는 최소 40ms 간격으로 setState를 호출하고, build 안에서 상세 분석과 dynamics를 다시 만든다(`lean_run_summary_screen.dart:274`, `:307–315`). 12,000개 샘플로 상세 생성+dynamics만 20회 측정했을 때 호스트 테스트 중앙값 **2.519ms**, 최대 **4.039ms**였다. 이 수치만으로 주된 병목이라고 할 수는 없다. 세션별 계산 결과 캐시는 간단한 개선 후보이며 전체 화면 시간이나 실기기 프레임 시간으로 해석하지 않는다.
5. **소스 정리는 성능 작업과 구분.** Dart 93개 파일 중 main의 import/export/part 그래프 밖에 6개가 있었다: `loading_screen.dart`, `drive_thresholds.dart`, `region_photo_service.dart`, `revv_copy.dart`, `ux_contracts.dart`, `corner_brackets.dart`. 테스트·계약 문서·다른 진입점 사용을 확인한 뒤 정리할 후보이지 안전한 삭제 목록은 아니다. 도달하지 않는 Dart 코드 삭제를 설치 용량 감소로 바로 환산하지 않는다. `record`와 `flutter_sound`는 현재 PTT에서 둘 다 사용하므로 단순 중복 패키지로 제거하지 않는다. Debug 시뮬레이터 앱 크기는 App Store 설치 용량 근거로 사용하지 않았다.

## UI/UX 제안: 오류와 별개

- **루트가 많은 지도는 유지한다.** 선택된 Route Promenade의 굽은 선, 57km/89분, 주행 시작 버튼은 현재 시뮬레이터에서 식별 가능했다. 최초 진입에서 주변 루트가 화면 밖에 있으면 사용자는 데이터가 없는 앱으로 오해할 수 있으므로, 로드 완료 후 주변 루트 경계를 보여주는 초기 카메라와 지역별 개수 표시를 우선 검토한다. 기존 9월 7일 최초 카메라 관찰과 연결한 제안이며 이번에 새 설치를 재현하지 않았다.
- **총 주행 시간과 진입 이동 시간을 구분한다.** 한국에서 몬트리올 루트를 구경하는 상황처럼, 루트의 89분이 현재 위치에서 출발해 돌아오는 전체 시간으로 읽히지 않도록 한다. 프리뷰에 지역/진입 방향/시작점까지 이동 여부를 명확히 표시하면 시작 전 판단이 쉬워진다. 이는 전환율 실험을 하지 않은 제품 제안이다.
- **저장 실패에서 탈출 경로를 설계한다.** 현재 수정은 실패 시 Retry만 허용하고 Home/뒤로 가기를 막는다(`lean_run_summary_screen.dart:332`). 데이터 보존 의도는 맞지만 지속 실패 시 사용자가 갇힌다. 별도 복구 사본 저장에 성공했다는 보장이 있을 때만 ‘나중에 다시 저장’을 제공하고, 보장이 없을 때는 명시적인 폐기 확인을 둔다. 버튼만 다시 활성화해 저장 실패를 숨기면 안 된다.
- **설정에서 권한을 바꾼 뒤 상태를 재확인한다.** Finder의 설정 열기 함수는 설정 앱만 열고, shell의 resume 처리에는 위치 권한 재확인이 없다(`lean_route_finder_screen.dart:1237`, `lean_app_shell_screen.dart:111`). 원래 거부 상태가 남는 경로를 소스에서 확인했다. 실제 설정 앱 왕복은 이번에 재현하지 않았으므로 별도 수동 검증 항목이다.

- 작은 화면 기존 7개 테스트: 기본 글씨 5 통과/2 실패, 1.5배 글씨 4 통과/3 실패. 실패 지점은 위 UI 넘침이다.

- 현재 iPhone 16e/iOS 26.3 시뮬레이터 미리보기 화면 확인/캡처. 실제 휴대폰 주행, 잠금/백그라운드, 현지 GPS, Release/Profile 메모리·배터리 측정은 미실시.

1. 복구 파일의 주행별 소유권·저장 완료 처리 → 동시 주행 재현 테스트를 정상 동작 검증으로 바꾸기.
